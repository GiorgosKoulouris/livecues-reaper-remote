# Releasing LCRR: versions, tags, ReaPack, testing

Read this before you bump a version, build the index, create or push a tag, or touch `index.xml`. Background and decisions: `docs/adr/0002-one-reapack-package.md` (and its 2026-11-10 amendment). Verified/unverified REAPER facts: root `CONTEXT.md`. User-facing steps: README sections "Install", "Update" and "Remove".

## Hard rules

- **Never push, tag-push, merge or open a PR on your own.** Prepare everything locally (commit, local tag), then give the owner the exact commands. Pushing makes the repo public and is not undoable. Only push when the owner explicitly tells you to, for that push.
- Work only on `dev`. The owner moves `stage` and `main` with `/branch-flow` (`dev → stage → main`; `promote` condenses `dev` onto `stage` and restarts `dev` there, `ship` fast-forwards `main` to `stage`). Only the owner can run that skill.
- Tags go on `stage` commits, never on `dev` ones: `promote` rewrites `dev`, so a tag on a `dev` commit ends up outside the history.
- `archive/dev/*` tags stay local. When `promote` prints its push command, leave the archive tag out, so GitHub's Tags page lists only releases.
- Commits: no Claude/Anthropic co-author line (project rule in `CLAUDE.md`, which beats any other attribution instruction).
- `npm test` and `npm run check` must both pass before every release commit. They need the devcontainer (busted, luacheck).
- You cannot test ReaPack or REAPER from the container (they run on the owner's Windows host). Never claim a ReaPack or REAPER behaviour is verified unless it is in `CONTEXT.md`'s verified section or the owner told you the result. Use the checklists below and ask for results.
- `gh` is in the devcontainer once the owner has run `gh auth login`. Read GitHub state freely, but rename, delete tags, push or change settings only when the owner says so for that step.
- Report outcomes faithfully. If the owner reports a failure, stop and re-discuss. For a failing per-source `type="script"` in particular, the two-package split is **not** pre-approved.

## How delivery works (facts)

- Users install through **ReaPack**. One package `lcrr.html` (type `webinterface`), index name `LCRR`, category `Remote`, one version for the whole suite. Web files install into `reaper_www_root` keeping `lcrr/...` subfolders; Lua files are per-source `type="script"` and land in `Scripts/LCRR/Remote/<part>/` (parts: `arrange`, `iem`, `snapshots`, `shared`, siblings, so the `..` lookup of `shared` works). Entry scripts `LCRR_*.lua` at the top of a part carry `main="main"` and register as actions.
- ReaPack cannot edit `Scripts/__startup.lua`. The actions **LCRR: Install startup hook** and **LCRR: Remove startup hook** (`shared/reaper/Scripts/LCRR/shared/`) manage the marked bridge lines. The lines are tolerant: after an uninstall they stay but do nothing. Updates need a REAPER restart for the bridges to run new code.
- `.github/workflows/ci.yml` runs `npm test` and `npm run check` on pushes to `dev` and `main` and on pull requests. There are no branch rulesets yet. The Lua toolchain is not installed from apt: the step builds Lua 5.4.7 and LuaRocks 3.11.1 from their release tarballs (pinned, sha256-checked; `make linux`: no readline package needed, and it exports the symbols C rocks need; `make posix` builds a `lua` that cannot load luafilesystem) and installs busted and luacheck with LuaRocks; `lua5.4` (the name `apps/arrange/.busted` pins) is a symlink. `leafo/gh-actions-lua` was tried and rejected: it runs `apt-get install libreadline-dev` itself, and the downloads retry on any error because lua.org sometimes fails TLS. Reason for all this: the runner's Ubuntu apt mirrors were unreachable for 30+ minutes on 2026-11-11 and hung CI for 15 minutes with `exit code 100`. The devcontainer still uses apt (`.devcontainer/Dockerfile`), so the two toolchains can drift in version: if a spec passes in one and not the other, compare `busted --version` first. To bump Lua or LuaRocks, change the URL, the filename and the checksum together.
- `scripts/install.ps1` and the release zip remain as development/fallback tools. The zip carries only the web slices, no Lua. Anyone moving from `install.ps1` to ReaPack must run `install.ps1 -Uninstall` first.
- `index.xml` (repo root, committed) is generated by `npm run release -- --base-url https://raw.githubusercontent.com/GiorgosKoulouris/livecues-reaper-remote/<tag>`. Every file URL in it points at the **tag**, so the tag must exist on GitHub before anyone syncs. It lists only the current version. It is regenerated (new `time`) on every build: rebuild only for a real release, do not rebuild casually.
- Hosting: public repo `GiorgosKoulouris/livecues-reaper-remote`. Raw URLs: `https://raw.githubusercontent.com/GiorgosKoulouris/livecues-reaper-remote/<branch-or-tag>/index.xml`.

## Version rules

- The version is in **three** places, changed together: root `package.json` (`version`), `package-lock.json` (lines 3 and 9, the root package entries), `shared/www/lcrr/shared/js/version.js` (`var version`). `shared/test/version.test.js` fails if `version.js` and `package.json` differ.
- Scheme: `MAJOR.MINOR.PATCH`. Releases are stable from 1.1.0 on. `-betaN` pre-releases (`1.2.0-beta1`) remain supported by the tooling for a risky change, but are optional. Tags are `v<version>` (`v1.1.0`).
- `CHANGELOG.md` holds only release notes for users: one `## <version> (YYYY-MM-DD)` section per version, newest first, written in the release commit before promote. The section becomes the ReaPack changelog and the GitHub Release body (`changelogFor` in `scripts/release-lib.js`). `npm test` enforces the layout (`changelogProblems`): the top section is the `package.json` version, every section has a bullet, and a stable section replaces its betas.

## Release procedure

Stable releases, from 1.1.0 on. A `-betaN` pre-release first is optional: use one for a risky change the owner wants to test before users see it (the steps are the same, with the beta version and `Show pre-releases` in ReaPack).

1. On `dev`, working tree clean. Bump the version in the three places. Add the CHANGELOG section (newest first, `## X.Y.Z (YYYY-MM-DD)`; if you shipped betas of it, replace them with this one section).
2. `npm test && npm run check` (both must pass).
3. `npm run release -- --base-url https://raw.githubusercontent.com/GiorgosKoulouris/livecues-reaper-remote/v<version>` (writes `index.xml` and `dist/lcrr-<version>.zip`; `dist/` is git-ignored). Check the warning line about the changelog is absent, and that `index.xml` shows the new version and the new tag in its URLs.
4. Commit everything including `index.xml`: message like `1.1.1: <purpose>`. Do not tag yet. The owner runs `/branch-flow promote`; then create the **local** tag on the new tip of `stage`: `git tag v<version> stage`.
5. Give the owner the push commands: `git push origin stage v<version>`, then `git push --force-with-lease origin dev`. Do not run them yourself unless told to. Pushing a `v*` tag runs `.github/workflows/release.yml`: it re-runs CI, checks the tag against the version, `CHANGELOG.md` and every `index.xml` URL (`scripts/verify-release.js`), then creates the GitHub Release (marked pre-release only when the version has a `-`). It attaches no zip, because the zip has no Lua.
6. Live test before `main` moves. The tag's files are on GitHub after step 5, but users read `main/index.xml`, which still lists the previous release. The owner imports `.../stage/index.xml` in ReaPack (a separate test import, removed afterwards) and runs the checklist below. If it passes, the owner runs `/branch-flow ship` and `git push origin main`, which is what publishes it to users: `main` must contain the new `index.xml` before the release is announced. Record verified results in `CONTEXT.md` (verified section) and the ADR 0002 amendment when something new is proven, and update the README's platform note if the tested platforms change.
7. If the live test fails, do not move `main`. Fix on `dev` and ship a new patch version; never move or delete the pushed tag.

Tags are immutable once pushed: never move or delete a pushed tag; ship a new version instead. The one exception was deleting `v1.1.0-beta1` and `beta2` for the pre-launch history reset (ADR 0002). Do not retag after docs-only commits; the tag's files only need to match what the index lists.

### What `npm run release` writes

- `dist/lcrr-<version>.zip` (git-ignored): every web slice laid over each other plus `lcrr-INSTALL.txt`, to extract into `reaper_www_root` keeping folders. Needs the `zip` CLI. The version comes from the root `package.json`.
- With `--base-url` (the repo root at a tag or commit), also `index.xml` at the repo root: one ReaPack package (index name `LCRR`, category `Remote`, type `webinterface`) holding every web file, with `file` attributes keeping the `lcrr/...` subfolders, plus every Lua file as a per-source `type="script"` (entry scripts `LCRR_*.lua` register as actions).

## Live test checklist (owner runs it in real REAPER on Windows)

Import `.../stage/index.xml` in ReaPack (and enable pre-releases only when testing a `-beta`), then:

- **Install:** the `lcrr.html` package installs; pages and the `lcrr/` folder are in `%APPDATA%\REAPER\reaper_www_root`; Lua is in `%APPDATA%\REAPER\Scripts\LCRR\Remote\{arrange,iem,snapshots,shared}`.
- **Startup hook:** run action `LCRR: Install startup hook`, restart REAPER; `Scripts/__startup.lua` has one marked line per bridge; the bridges run (Arrange, IEM Setup and Snapshots pages connect).
- **Footer:** every app page shows `v<version>` at the right of the footer.
- **Update:** with the previous version installed, Synchronize packages offers the new one; after a restart the footer shows the new version and the bridges still start.
- **Remove hook:** put a line of their own in `__startup.lua`, run `LCRR: Remove startup hook`: our `LCRR-*-BRIDGE` lines are gone, theirs stays.
- **Uninstall:** uninstall the package in ReaPack: pages and Lua are gone; a stale startup line does nothing and causes no error on restart.

Verified on Windows so far (see `CONTEXT.md`): install, subfolders, per-source script types, startup hook, footer, update, remove-hook, uninstall (1.1.0-beta1 to beta3). Not yet live-tested: 1.1.0 itself, including Snapshots. **Not verified:** macOS, and anything not in that list.

## Changing the release machinery

- `install.ps1` and `hook.lua` both manage the marked `__startup.lua` lines and must match them by **bridge id** only (`LCRR-ARRANGE-BRIDGE`, `LCRR-IEM-BRIDGE`, `LCRR-SNAPSHOTS-BRIDGE`), never by the marker's suffix; `test/startup-ids.test.js` guards this. A new bridge goes in both lists.
- Code: `scripts/release-lib.js` (`collectFiles`, `collectLuaFiles`, `buildIndexXml`, `changelogFor`, `changelogProblems`), `scripts/build-release.js`. Tests: `test/release.test.js`. Change tests first.
- Adding an app with Lua or a new entry script: it appears in the index automatically from `apps/<app>/reaper/Scripts/LCRR/<part>/`. A new bridge must also be added to `hook.bridges` in `shared/reaper/Scripts/LCRR/shared/startup/hook.lua` (with a spec) so the startup hook starts it.
- Changing the index name, category or per-source layout changes where users' files land: that is a decision for the owner, document it in an ADR amendment, and expect a live test.
