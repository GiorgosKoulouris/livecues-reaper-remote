# IEM Setup

The engineer's admin page for the in-ear mixes Monitor plays (`lcrr-iem.html`). Decisions: `.scratch/iem/spec.md`. REAPER facts (measured in the issue 01 spike) are in the suite `CONTEXT.md`.

## Terms

- **Mix**: a track named `IEM_<name>`, exact and case-sensitive, with something after the prefix: Monitor's rule, so the two agree. Shown by `<name>`. IEM Setup also shows mixes Monitor does not list yet (no receive or no output).
- **IEMs folder**: the first track named `IEMs`. A mix inside it is *in the folder*; any other is a **stray** (shown, flagged, to be adopted by a later issue). A folder track at `I_FOLDERDEPTH` 0 is a plain track and holds nothing.
- **Source**: every other track, in project order, with its folder `depth` (0 at the top).
- **Send**: a receive of a mix. Level `vol` is linear gain; `mode` is `I_SENDMODE` (3 = post-FX pre-fader, what IEM Setup creates; anything else gets the POST or PRE mark); `muted` is the send's own mute.
- **Output**: a hardware output of a mix, `{ channel, mono }`, `channel` 0-based. A mix with none is "No output".
- **Double feed**: a folder track and one of its children both feed the same mix.

## The `state` command (issue 03)

Request `cmd=state`. Reply `{ v, command, project: { name, path }, status: "ok", colour, folder?: { guid, is_folder, tracks_after }, mixes: [ { guid, name, in_folder, master_send, outputs: [ { channel, mono } ], sends: [ { source (GUID), vol, muted, mode } ] } ], sources: [ { guid, name, depth, is_folder } ], device: { channels: [name] }, master_outputs: [ { channel, mono } ] }`. `device.channels` are the audio device's output names (`GetOutputChannelName`), empty while the device is closed; `master_outputs` are the master track's own hardware outputs (issue 06). `folder` is absent when no track is named `IEMs`; `tracks_after` is true while tracks sit after its last member (what makes the page offer Move to end). It is also true for an emptied folder (a plain track) with tracks after it, on purpose: `create` reopens the folder right after itself, so the new mix would not sit at the end, and Move to end then moves that one track. `colour` is the shared colour as `rrggbb`: the project's (ExtState `LCRR_IEM` / `colour`), else the default `3b82c4`. Mixes and sources are in project order. Refusals are `{ status: "refused", error: { code } }`: `bad_request`, `request_truncated`, `unknown_command`, `internal`. Wording is `words.js`; the recorded replies are `test/fixtures/bridge-replies.txt`.

## The write commands (issue 04)

Each names tracks by GUID, answers `{ v, command, project, status, ... }` and is **one undo block** (`Undo_BeginBlock2`/`Undo_EndBlock2`, `lib/core/undo.lua`); a refusal is decided before the block opens, so it leaves no undo point. Refusals are `{ status: "refused", error: { code } }`.

- `create` (`name`) -> `{ guid, folder_created }`. The name is trimmed and the prefix is the bridge's. Codes `empty_name`, `duplicate_name` (exact, case-sensitive, any mix, stray or not). With no cue track in the project the first create also makes it, in the same undo step (see `cue` below). The first create adds the `IEMs` folder at the end of the list (depth 1, master send off, shared colour) and the mix inside it (depth -1). Later creates go after the folder's last member: that member's depth moves to the new mix (the old one becomes 0), so a folder nested in another keeps closing both. An emptied folder (plain, depth 0 or a negative closing depth) is reopened: it becomes 1 and the mix takes its old depth minus one. Folder and mix get master send off and the colour; a folder that already exists is not touched otherwise.
- `create` also takes an optional `copy` (GUID of a mix; issue 09): the new mix gets a send from every source that feeds that mix, with the same level, pan, mute and signal point (`D_VOL`, `D_PAN`, `B_MUTE`, `I_SENDMODE`), inside the same undo step ("IEM Setup: create mix"). Not its output. A send from another mix or from the IEMs folder is not copied; several sends of one source are all copied. Refused before the block opens: `track_gone`, `not_a_mix` (the name is checked first). The page: a "Copy from" list in the create form (None, then each mix); the request carries only GUIDs.
- `rename` (`guid`, `name`) -> `{ changed }`. Codes `track_gone`, `not_a_mix`, `empty_name`, `duplicate_name`. A mix's own name (even one a duplicate shares) is `changed: false`, no undo step, so duplicates can be renamed apart.
- `colour` (`colour`, `rrggbb`) -> `{ colour }`. Code `bad_colour`. Stored in the project, applied to the folder and every mix inside it (not to a stray, not to sources).
- `move_to_end` (`guid` of the folder) -> `{}`. Codes `track_gone`, `not_the_folder`, `nothing_to_move`. Selects the folder and its members, `ReorderSelectedTracks(CountTracks, 0)`, restores the engineer's selection. Never runs by itself.

- `delete` (`guid` of a mix) -> `{}`. Codes `track_gone`, `not_a_mix` (the folder, a source and a bare `IEM_` are refused). `DeleteTrack` takes the mix's sends with it. REAPER does not repair folder depth, so in the same undo step ("IEM Setup: delete mix") a mix that closed levels (depth < 0) adds them to the previous track's depth (the folder's last mix gives the previous member its closing; the folder's only mix leaves the folder at 0, or at a negative depth if the mix closed beyond it; a stray inside another folder works the same way), and a mix that opened a folder of its own (depth > 0) adds that to the track that closed it. A mix that is the first track of the project has no previous track to hand its closing depth to; nothing is repaired and the delete still succeeds (a malformed project, covered by a spec). The page's key is press-and-hold (1 s, `LCRR.shared.hold`) in each mix's More group, through `write()`.

- `output` (`guid` of a mix, `channel` 0-based or `none`, `mono` `1`/`0`) -> `{ changed }` (issue 06). Set, replace and clear are one operation in one undo step ("IEM Setup: set output"): a mix with an output has it changed in place (so there is never more than one), `none` removes it. Mono is `I_SRCCHAN` 0 with `I_DSTCHAN` `channel | 1024`, stereo `I_DSTCHAN` `channel` (suite CONTEXT.md). Codes `track_gone`, `not_a_mix`, `multiple_outputs` (a mix with several outputs is read-only: the bridge refuses set and clear), `bad_channel` (not a whole number, outside the device, or a stereo pair running past the last channel), `no_device` (a set while the device is closed; a clear still works). An output already as asked is `changed: false`, no undo step.

- `cell` (`source` GUID of a source, `mix` GUID of a mix, `on` `1`/`0`) -> `{ changed }` (issue 07). On creates a send source -> mix, `I_SENDMODE` 3 (post-FX pre-fader) and `D_VOL` 1 (0 dB), set explicitly because REAPER's new-send defaults are post-fader; off removes **every** send of the pair (from the source's side, highest index first) with no warning. The request carries the wanted state, not a toggle, so a stale page finds the cell already as asked: `changed: false`, no undo step. One undo step each ("IEM Setup: switch cell on" / "switch cell off"). Codes `track_gone` (source or mix), `not_a_mix`, `not_a_source` (a mix, or the IEMs folder). The page: every cell is a key (44px) through `write()`, so one request is in flight and the keys are disabled while it is out. Several sends in one pair still show as one cell (`sends` count, first send's level).

- `row` (`source` GUID) and `column` (`mix` GUID), each with `on` `1`/`0` -> `{ changed, count }` (issue 08). A row is one source across every mix (stray ones too), a column is one mix across every source (never another mix or the folder); the request carries only that ID, the bridge works out the other side. On adds only the missing sends (as `cell` does: `I_SENDMODE` 3, 0 dB) and leaves existing sends alone (level, mode, mute); off removes every send of each pair, with no warning. Removals run highest send index first per source, across all its pairs (sends are numbered per source). Nothing to do: `changed: false`, no undo step. One undo step each ("IEM Setup: switch row on/off", "switch column on/off"). Codes `track_gone`, `not_a_source` (row), `not_a_mix` (column). `lib/core/bulk.lua`. The page has no keys for these: the commands stay in the bridge (and `client.js`, `core.js`) but the page never sends them.

- `adopt` (`guid` of a stray mix) -> `{}` (issue 10). One undo step ("IEM Setup: adopt mix"): the stray leaves its place (neighbours' depths repaired as `delete` does, its own depth set to 0), moves to the end of the IEMs folder with `ReorderSelectedTracks(before, 0)` (the folder is created at the end first when there is none; the depth edits are `create.open_slot`, shared with `create`; the engineer's selection comes back), master send off, the shared colour, and every send it receives set to `I_SENDMODE` 3 from the source's side (level, pan and mute kept). Its hardware outputs are untouched, so several outputs stay and show read-only. Codes `track_gone`, `not_a_mix` (also the folder), `not_a_stray` (already in the folder). A stray that opened a folder of its own leaves that folder's children outside it, as `delete` does. `lib/core/adopt.lua`. The page: an Adopt key (press-and-hold) in a stray's More group, through `write()`.

- `cue` (no fields) -> `{ changed, created, guid, added, protected }` (IEM Mix issue 07). The **cue track** is the track named `IEM-Cue` (exact, case-sensitive, never starting with `IEM_`, so it is no mix; the first one in project order, a later one is an ordinary source). One undo step ("IEM Setup: create cue"): when missing, the track is made last in the IEMs folder (`tracks.open_slot`, the folder created first when there is none), master send off, shared colour; then every mix (stray or not) with no send to it gets one, post-fader (`I_SENDMODE` 0) at level 0 (linear gain 0, silent). **Solo defeat** (`B_SOLO_DEFEAT` = 1, so a source soloed in REAPER does not silence a mix or the cue track) is turned on for the cue track and every mix, stray or not; `protected` counts the tracks it was turned on for. Running it again adds only the missing sends and the missing solo defeat (the repair for a project made before this, or a mix the engineer switched back); with nothing missing it is `changed: false`, no undo step. `lib/core/cue.lua`. No refusals of its own. **`B_SOLO_DEFEAT` is unverified on real REAPER** (see "Still unseen"); `cue.SOLO_DEFEAT` is the one place to correct it.
- The cue track in the other commands: `create` (with or without `copy`) and `adopt` give the new or adopted mix its cue send and solo defeat in their own undo step (`cue.join`; adopt only adds the send when the stray has none; `copy` never copies a cue send). **When the project has no cue track, the first create or adopt makes it** (`cue.ensure`: the track after the new mix, last in the folder, master send off, a send from every mix, solo defeat on all), so the engineer never has to press Create cue; the hardware output is still chosen by the engineer on the page. `tracks.is_source` excludes the cue track, so `cell`, `row` and `column` refuse it as a source (`not_a_source`) and it is no row in `state.sources`; as it is no mix, nothing can be switched on into it, so no routing loop can be made from the page. `output` also takes the cue track's GUID (set, replace, clear, same codes, "IEM Setup: set output"); any other non-mix is still `not_a_mix`.
- `state` adds `cue: { guid, outputs: [ { channel, mono } ], missing, unprotected }` (absent when there is no cue track); `missing` counts mixes with no send to it and `unprotected` the mixes and the cue track without solo defeat. The page reads `unprotected` too (`core.cueOffer`). The page, through `write()`: a Create cue key (labelled Repair cue while `missing > 0` or `unprotected > 0`; hidden when nothing is to do) and the cue's output picker (`core.cueOffer`, the same options as a mix's). While the cue track has no output (`needsOutput`) its label reads "Cue output: choose the headphones" and its hint says Listen is silent until one is chosen. Monitor's mix list is unaffected: `IEM-Cue` has no `IEM_` prefix (`core.test.js` runs the shared listing rule over the recorded `state_cue`).

There is no lock command and no lock on the page (`docs/adr/0001`).

## Page behaviour (this slice)

- Connection states and the heartbeat are Arrange's: the page knows the bridge runs only from its heartbeat changing; if it stops, a banner says so and no editing is possible.
- The page reads `state` when it becomes ready, every 3 s while visible, and when the tab is shown again. An identical reply leaves the grid untouched, so a refresh never moves its scroll.
- Grid: sticky row and column headers, name filter (case-insensitive substring), ON cells with the level read-only (dimmed and struck through when muted), POST/PRE tag on a send that is not post-FX pre-fader, `2x` tag on a double feed, "No output" in the column header. A send from a track that is not a source row (another mix) is not drawn.
- **No lock** (`docs/adr/0001`). `core.canEdit(phase)` is the single gate (a live bridge); `iem.js`'s `write()` checks it and every write goes through it, so every write command reuses it. Adopt and Delete are press-and-hold. A write shows no confirmation line: the grid or panel changing is the confirmation, and a refusal shows in the sticky bar.
- **Controls** (shown once the project is read): a strip above the grid (the filter, the tag legend and one disclosure key per setup job: Mixes, Folder, Cue, each with a status in words; the project name is in the bar); one panel open at a time, and the first read opens Mixes only when the project has no mixes. Mixes: a name field, Copy from (once a mix exists) and Create; Folder: the colour input (a change sends `colour`) and Move to end (live only while `folder.tracks_after`); Cue below. A mix's column header holds its output picker and More; More holds Rename (turns the name into a field with Save and Cancel; Enter and Esc work), Adopt (strays) and Delete. Names are checked by `core.checkMixName` before sending (the bridge checks again); a refusal is worded by `words.js` and stays on screen until the next attempt. After every write the page re-reads the project.

## Conventions

- Names are exact and case-sensitive everywhere (`IEM_Bass` and `IEM_bass` are two mixes), as in Monitor. The spec does not say so; this is the decision.
- Cores refuse through `tracks.refusal(code)` and look a mix up with `tracks.find_mix(list, guid)` (`track_gone`, `not_a_mix`), so a new core does not copy that prelude.
- A blank channel name from the device is shown by its number (`words.channelName`).
- Touch targets in `iem.css` are a hard-coded `44px`; `DESIGN.md` has no touch-target token yet (open).

## Hardware output (issue 06)

- Picker per mix in its column header, None, Mono per device channel, Stereo per pair from an even channel, plus the current output if the list does not offer it. Labels carry REAPER's channel names ("Mono 2 Output 2"). A mix with several outputs shows its outputs as text and "N outputs, read-only", no picker. With the device closed the picker is disabled with a note and the existing output is shown by number.
- A shared output is flagged in the header, never refused. `core.outputClashes` compares occupied channels (stereo = channel and channel + 1), against other mixes' outputs (all of them) and the master's hardware outputs.
- An open picker holds the render gate (`core.createPickerGuard`, from focus or press until a choice or blur), so a refresh cannot close it; the deferred rebuild runs once afterwards. The choice goes through `write()`.

## Measured on real REAPER: reorder rewrites folder depths (issue 11)

`ReorderSelectedTracks` rewrites folder depths around the track it moves, even when the move changes nothing: adopting the first of two strays sitting right below an emptied folder left `UserB` with a closing depth of -1 that nobody set, and in the second adopt the call put the previous member's depth back after the core had changed it, so the whole operation changed nothing. So `adopt` skips the reorder when the stray is already at its slot and writes the two depths it needs (the old last member 0, the stray its closing depth) after any reorder. Whether a real move (a stray above the folder, or no folder yet) leaves other depths rewritten is still unseen; the fake cannot show it.

## Verified on real REAPER (issue 11, 2026-11-09)

The whole path was walked on a copy of a project (`podium-dummy3`, REAPER 7.82, Windows, a two-output device, the page in Chrome with Monitor open): create, copy from a mix, rename, colour, Move to end, delete by hold, set/replace/clear outputs, matrix cells, row and column toggles, adopt (a stray below an emptied folder, a stray above the folder and no folder yet), the banner with the bridge stopped, both bridges after a REAPER restart, the tablet layout. Each operation undoes as one step. Only adopt needed a fix (the reorder finding above); the rest worked as built. The unit specs run against a fake REAPER, so a bug that only real REAPER shows (like that one) is caught by this kind of walk, not by `npm test`.

## Snapshot commands (issues 10 and 11; used by IEM Mix, not by this page)

Snapshots are stored in project ExtState (section `LCRR_IEM`), which ignores undo: these three commands open **no undo block and add no undo step**, and nothing they do can be undone. Refusals are `{ status: "refused", error: { code } }`.

- `snapshots` -> `{ snapshots: [ { name, saved (epoch seconds), mixes, sends } ] }` in save order. Reads only the index, never a snapshot's contents. Code `unreadable` (the stored index is not one this version wrote; it is never guessed at).
- `snapshot_save` (`name`, optional `overwrite` `1`) -> `{ name, overwritten, mixes, sends }`. The request carries only the name; the bridge reads the contents: for every mix with at least one send (the same reading `state` gives), each send's `D_VOL`, `D_PAN` and `B_MUTE` by source GUID, and the mix's master level (its first hardware output's `D_VOL`; none when it has no output). The name is trimmed, at most 40 characters, no control characters, unique and case-sensitive. An overwrite keeps the snapshot's place in the list and refreshes `saved`. Codes `empty_name`, `bad_name`, `name_too_long`, `duplicate_name` (taken, no `overwrite`), `not_found` (`overwrite` on a name not saved), `nothing_to_save` (no mix has a send), `unreadable`.
- `snapshot_delete` (`name`) -> `{}`. Codes `empty_name`, `bad_name`, `name_too_long`, `not_found`, `unreadable`.
- `snapshot_recall` (`name`, optional `mix`: a mix GUID) -> `{ name, mixes, sends, skipped, missing }`. Writes level, pan and mute of each stored send (to the receive on its mix from the same source) and each mix's master level, matched by GUID, in **one undo step** (`IEM Mix: recall snapshot <name>`; the only snapshot command that touches the project). `sends` and `mixes` count what was written; `skipped` counts stored sends with no receive now (source or mix gone, or pair no longer routed); `missing` counts mixes gone. A send added since the save is left alone; with `mix`, every other mix is untouched. Nothing written means no undo step. Codes `empty_name`, `bad_name`, `name_too_long`, `not_found`, `unreadable`, `track_gone`, `not_a_mix` (`mix`), `mix_not_saved` (the snapshot holds nothing for that mix). All refusals come before any write.
- Storage (`lib/core/snapshot_store.lua`): an index key `snapshots` and one key `snapshot.<id>` per snapshot, each a single line (no newline in a value). The list reads only the index, so it and every reply stay small however large a snapshot is; a snapshot of 12 mixes by 120 sources (1440 sends, about 100 KB) is a spec. The store can read a snapshot back (`store.read`) for recall. Contents are written before the index lists them.
- Not measured on real REAPER: how a value of that size round-trips through `SetProjExtState` and the .rpp (ExtState replies of 4 MB are measured; project ExtState size is not), and that a single-line value of this form is stored verbatim.

## Still unseen

- `B_SOLO_DEFEAT` on real REAPER 7.82: that `GetMediaTrackInfo_Value` and `SetMediaTrackInfo_Value` take this name with 1 as on, that it reads back, and that an undo of the create step restores it. The fake models it only as the name the core uses.
- Channel names on a multi-output interface: the test device had two outputs ("Out 1", "Out 2"). The labels assume `GetOutputChannelName` names are usable as given, and the stereo pairs from even channels suit consecutive pairs only. Whether REAPER accepts a stereo pair starting on an odd channel is untested (the picker never offers one; an existing one is shown).
- `state` timing on a project with hundreds of tracks (it runs on REAPER's main thread, every 3 s per open page), and the timing of a column toggle there.
- `ReorderSelectedTracks` when the IEMs folder is itself nested in another folder, or the track after it closes a parent: the spike and the walk used top-level folders. Move to end does not adjust depths itself.
- Whether a real adopt move leaves other tracks' depths rewritten when a folder member sits elsewhere than the end (reorder rewrites depths around the moved track, see above); the walk's layouts came out right.
