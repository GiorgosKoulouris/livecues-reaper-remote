# IEM Mix

One page to see and balance every in-ear mix. Spec: `.scratch/iemmix/spec.md`. REAPER API facts are in the root `CONTEXT.md`.

## Terms

- **Mix**: a track listed by Monitor's rule (`IEM_<name>`, exact and case-sensitive, a name after the prefix, at least one receive and one hardware output). A **column**.
- **Source**: a track with at least one send to a listed mix, matched through each receive's source track index. A **row**, in project order.
- **Cell**: one source in one mix.

## Behaviour (issues 03 to 05: grid, lock, panel, mute and pan)

- Columns are the listed mixes in project order. A name on more than one track, listed or not, is marked not editable (every cell of a listed one `readOnly`), the same refusal as Monitor's `findMix`; each listed one still shows.
- A cell shows the send's level as a look-only slider (no drags) with the number in dB, dimmed and struck through when the send is muted. No send, no cell: an empty cell is inert. Several sends of one source to one mix show the first level (lowest receive index) with a `2x` tag, read-only.
- A source whose track is muted is marked "Track muted" in its row header (a muted track silences its post-FX pre-fader sends).
- Sticky row and column headers; a name filter on source rows. Hovering a cell with a mouse lifts its row and column. The Source column has a drag handle on its header (120 to 480 px, never so wide that no mix column fits; arrow keys too, double-click for the automatic width), remembered per browser in `localStorage`; once sized, long names are cut with an ellipsis. Built for 768px and wider; below that the panel stacks under the grid.
- Reads: `NTRACK;TRACK` every 250 ms (the shared poller). The receives of every listed mix are read once a second in requests of up to 900 URL characters, sent side by side, and at once when the layout changes. Offline (2 failed polls) keeps the last grid and shows a banner.
- A reply is applied only under the layout (`layoutKey`: track numbers, names, receive and hardware output counts) it was requested for. A partial reply, a missing-send line or a failed request never removes a cell. When the layout changes the old receives are dropped (source numbers shift with the track list) and the page keeps its last picture until the new layout has been read in full or a sweep has ended under it.

### The lock and the panel (issue 04)

- The page opens locked. One Unlock tap enables every control; it relocks when the connection goes offline or another project becomes active, never on idle.
- The web API names no project, so the page keeps its own **project marker** in project ExtState (section `LCRR_IEMMIX`, key `project_id`), read in the same `NTRACK;TRACK` poll. At Unlock (`claimProject`) it reads the marker: if there is one it remembers it and writes nothing (a second tablet shares the ID); if it is empty it writes a random ID and needs the read-back to match. If the marker can't be read or the read-back differs the page stays locked and says why; there is no fallback to the track names. While unlocked (`markerHolds`) a changed, empty or absent ID relocks and cancels every drag, as a dropped connection does. The one poll already out when Unlock wrote the ID may still answer empty, so a just-written ID forgives one empty reply.
- A write can still land in the up to 250 ms between a project switch and the next poll: the API can't name the project a write goes to, so this gap stays open.
- `canEdit(phase, unlocked)` is the one gate. `writeAllowed(target, model.writeState(canEdit))` is the one stale check and the shared fader's `check`: it needs the gate open, a listed editable mix (not a duplicate name), and for a source row the same source still at that receive index and no repeated pair; the master (`SEND/0`, source -1) also needs its level read. It runs when each request would go out, so a change during a drag stops it with no final write. Locking cancels every drag.
- The panel sits beside the grid. A name opens a selection (`selectSource`, `selectMix`; the selection carries the track name and is dropped if the track at that number changes). A cell brings up its fader, highlighted (`selectCell`): the open panel stays if it holds the cell, otherwise a panel of the same kind opens for the cell's source or mix, and with none open the cell's mix. It works while locked. Clicking the cell already highlighted does nothing; an empty cell is inert; a read-only cell highlights its static row. A source panel has a row per mix that has a send; a mix panel has the master first, then its sources in project order. A repeated pair (`2x`) or duplicated mix shows its level with a note and no fader.
- The visible panel sends (and the mix master) are read on every 250 ms poll (`buildPanelRequests`), faster than the grid. Reads go through `model.apply(key, text, keep)`: `keep(track, y, field)` names the fields (`vol`, `muted`) a control is dragging or still writing; `holdSlot` keeps those from the screen. A drag writes through `model.setLocal` so the grid follows the thumb.
### Mute and pan (issue 05)

- Each editable source row in the panel has, in `.iemmix-prow-controls`, a pan control and a mute button beside the level fader; all three fit one row at 768px (panel 22rem: pan 6.5rem, mute 44px). The master row has a level only, and a `2x` pair or a duplicated mix is a static row with none of them.
- Mute is Monitor's: `createMuteWriter` sends the state worked out from the screen, never a toggle. Pan is a short slider (centre at the middle, shown "C", "L25", "R100") written as `SET/TRACK/<t>/SEND/<y>/PAN/<v>` by the same `createFaderDrag` as the level, with `setPanCommand` and a linear -1..1 mapping injected: one write in flight, at most one per 50 ms, release sends the value then `e` in one `;`-joined request (one "Adjust send pan" undo entry), the stale check at the moment each request goes out. The pan is clamped to -1..1 in `setPanCommand`; a pan read outside that range parks the thumb at the end.
- `pan` is read from the `SEND` line (`parseSendReply`) and is a held field (`HELD_FIELDS`), like `vol` and `muted`: a read never moves a control that is dragging or still writing. Both controls register in `ref.parts` (`muted`, `pan`); locking cancels a pan drag.
- The mouse wheel over a level fader (source, mix or master row; not pan) or an editable grid cell nudges it 0.5 dB per notch, wheel up louder (`wheel.decide`, pure, in `wheel.js`). 100 pixels (3 lines, 1 page, by `deltaMode`) is one notch. An event of a notch or more gives one step per whole notch and drops the remainder, because some wheels send 120 a notch. Smaller events (a trackpad) gather until they make a notch; a change of direction or the 400 ms idle wait clears them, and the page does not scroll while they gather. It acts only while unlocked and online (`editable()`); otherwise the listener does nothing and the page scrolls as normal. The listener is non-passive and calls `preventDefault` only when `decide` says it acts on a fader, including an up step that writes nothing. An up step never goes above the +6 dB cap; a level already above the cap is left alone by an up step but steps down from there. The lowest audible step is -60 dB (the fader's law, value = pos^4 x cap, puts it about 18% along the travel; the readout is -inf only at exactly 0): from silence or anything below -60 dB an up step goes to -60 dB, and a down step that would land below -60 dB writes silence (0). Steps go through the shared fader's `nudge` (`createFaderDrag.nudge`): the same stale check (`canWrite(ref.target())`), one request in flight and 50 ms gate as a drag; each step is worked out from the level on screen, which is the last level written; a burst is one move, with the `e` (one undo entry) sent once after 400 ms of no wheel (`wheelIdleMs`). The wait is held like a drag (a read cannot move the fader), no `e` goes out if the row went stale or the page locked meanwhile (locking cancels it), and a wheel step during a drag does nothing to it. Monitor has no wheel.
- Grid and panel share one wheel listener (on `.iemmix-panes`). A cell's first step that writes selects the cell as a click does, then goes through that row's fader, so there is one write path. The target is the element under the pointer (`elementFromPoint`), not `ev.target`, because browsers keep a wheel gesture on the element it began on. For the same reason the table is rebuilt only when its shape changes (`gridShape`); levels and selection are painted in place. One wheel gesture stays on what it began on (`wheel.createWheelLatch`), until 400 ms of no wheel, over the grid and the panel alike: an edit keeps changing that one level wherever the pointer goes, and a movement that began off an editable control keeps scrolling. So while unlocked the grid scrolls by starting over a name, an empty cell or the scrollbar. A panel rebuild finishes a burst (`finishWheel`) so it keeps its undo entry; it does not drop it as a drag is dropped.
- Alt-click resets: a grid cell or a panel level fader (source, mix or master row) to 0 dB, a pan control to the centre. Unlocked only. It writes through the control's own path (`nudge` then `finishWheel`: the stale check, one undo entry), acts on release like a click, and is skipped when the value is already there. A cell comes up highlighted first, as a click does; while locked an Alt-click on a cell is a plain click. A read-only cell has no reset. The press is stopped in the capture phase so it never starts a drag.
- Pan and mute are disabled (`disabled`, dimmed) while locked or offline, and every write still goes through `canWrite`.

### Listen (issue 08)

- Pure logic in `www/lcrr/iemmix/js/listen.js` (`LCRR.iemmix.listen`, loaded after `core.js`; tests `test/listen.test.js`); the wiring is one block in `iemmix.js`, and the keys are the `#iemmix-listen` strip above the grid (one key per mix, the one heard is pressed).
- The cue track is the first track named exactly `IEM-Cue`. A mix's cue send is its first send (`GET/TRACK/<t>/SEND/<y>`, `y` from `hwoutcnt` to `hwoutcnt + sendcnt - 1`: `listen.sendRange`) whose destination (the reply's last field) is the cue track. Once found only that `y` is read, once a second with the grid's sweep, in requests under the URL limit (cost: one read per mix); a layout change (cue track, mix numbers, names, `hwoutcnt`, `sendcnt`) drops what was found and reads in full again.
- A tap writes the send's level, `VOL/1` or `VOL/0`, with no `e` (no undo entry), all the changes of one tap in a single request. The only mix on, tapped: off. Another on, or several: the others to 0 and the tapped one to 1 (a tapped one that is on among several is the one left). A send counts as on at any level of 0.001 or more, because a REAPER undo can leave any level; the page never assumes the last tap still holds and shows what the reads say.
- A read begun before a write is dropped, and reads pause while the write is out. No cue track, or a mix with no cue send: its key is disabled with a note pointing to IEM Setup. A duplicated mix name is disabled too. A tap acts only through `canEdit` (the lock).
- Unverified on real REAPER: the cue send's destination field in a `SEND` line for `y` 1 and up (assumed the same shape as a receive's source field, as the API documents), and the page in a browser.

## Snapshots (issues 10 and 11: save, list, delete, recall)

- A Snapshots section sits under the panel's faders. The list is read through the bridge (`snapshots`) when the heartbeat of `LCRR_IEM` shows it running, on becoming ready, every 3 s and after each write; reading needs no Unlock. Save (a name field and a key) is a tap; Overwrite and Delete are press-and-hold keys (1 s, `LCRR.shared.hold`) on each row. The list is not rebuilt while a hold is down. Only the name travels; the bridge reads the levels, pans and mutes (commands: `apps/iem/CONTEXT.md`).
- All three controls are enabled only while unlocked, connected and with the bridge running (`snapshots.canWrite` plus `editable()`). With the bridge not running the section shows a note ("Snapshots need IEM Setup's bridge, which is not running in REAPER. Levels, pans, mutes and Listen still work.") and no controls; the rest of the page does not depend on it.
- Names are trimmed, at most 40 characters, unique and case-sensitive; `snapshots.checkName` checks before sending (the bridge checks again) and `bridge.nameFits` keeps the request under the URL limit. A refusal is worded by `snapshots.errorText` and stays until the next attempt.
- Recall: each snapshot row has a **Recall all** key and, while a mix is selected in the panel, a **Recall <mix>** key, both press-and-hold, through the same gate as the other writes (`editable()` plus the bridge, so unlocked only). Recall is one undo step in REAPER (unlike the other three) and overwrites what the musicians changed since the save; the standing note says so. It writes level, pan and mute of each stored send and each mix's master level, matched by GUID. REAPER's web API has no track GUIDs, so for one mix the page asks the bridge for `state` and finds the mix by name (`snapshots.findMix`; a name held by two mixes refuses). The request carries the snapshot name and the GUID, so a name of the widest characters can be too long for it and is refused as `request_too_long`.
- After a recall the note says what was written and what was skipped (`snapshots.recallText`: levels (sends and mix master levels) skipped because their source, mix or output is gone or no longer routed, mixes no longer in the project); sends added since the save are left alone. It stays until the next write. Recall does not fight a drag on another page: the last write wins and the page shows the result on its next read.

## Still unverified

- The send numbering on a mix with several hardware outputs. Measured only with one output (output `y=0`, first ordinary send `y=1`), so the page assumes outputs take `y` 0 to `hwoutcnt - 1` and ordinary sends follow from `y=hwoutcnt`. `listen.sendRange` is where the numbering is applied (`layoutKey` only reads `hwoutcnt` to notice a change). If it is wrong, Listen reads the wrong sends and may show a mix with no cue send.
- The project marker. `GET/PROJEXTSTATE/<section>/<key>` and `SET/PROJEXTSTATE/<section>/<key>/<value>` have never been measured here, nor their reply (assumed `PROJEXTSTATE\t<section>\t<key>\t<value>`, as `EXTSTATE`). Only the marker block in `core.js` knows the form. Also unmeasured: whether each project keeps its own ID, and whether writing it marks the project as modified.
- The fader and pan drags, the wheel on a real mouse and trackpad, the mute button and the panel layout on real hardware with real REAPER.
- The page in a real browser, with real REAPER and a real project size (the spec's issue 12 checks a real project).
